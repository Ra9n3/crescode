# Harmony engine (Phase 1)

- New framework-free module `src/engine/harmony/` (`types.ts`, `vocabulary.ts`, `analysis.ts`, `index.ts`). The brief suggested `src/orchestrator/harmony/`; the repository's convention places pure algorithmic code under `src/engine/`, so the module lives there. No React/Zustand imports, no new dependencies.
- Reuses `src/shared/schema/modes.ts` (MODES, MODE_NAMES, NOTE_NAMES, scalePitchClasses) and `src/shared/schema/chords.ts` (parseChord) — no duplicated scale or pitch-class data, no separate chord notation.
- Chords are discovered algorithmically from scale pitch classes and a catalog of 14 fundamental interval formulas; no per-mode chord tables. Cardinality-agnostic (7-note modes, 6-note Whole Tone, 8-note Diminished scales).
- Modal characteristic tones are derived by scale comparison (nearest same-third, same-cardinality, non-symmetrical relatives), not hardcoded per mode; symmetrical scales return an empty set with an explicit `symmetric` flag.
- Vocabulary/analysis functions are descriptive only: no progression generation, no scoring, no borrowing decisions. Manual chord entry, the chord editor, and the orchestral Generate workflow are untouched (no UI or store changes in this phase).
- All emitted chord symbols round-trip through the existing parser with identical pitch-class content, verified across all 144 tonic/mode combinations in `tests/harmony-vocabulary.test.ts` (25 new tests; suite total 83).

# Harmony engine (Phase 2 — section profiles)

- Extends `src/engine/harmony/` with `contours.ts`, `context.ts`, `profiles.ts` (types extended in `types.ts`, exports in `index.ts`). Still pure TypeScript: no React/Zustand, no new dependencies, no UI or store changes, manual workflow and orchestral Generate untouched.
- Schema: `Section.energy?: number` (0–1, optional, missing = neutral 0.5) added as the SINGLE canonical energy field — the spec assumes one exists; none did. Validated when present (mirrors the `Chord.locked?` pattern), documented in `project.schema.json`. Old files load unchanged.
- `resolveSectionIdentity`: free-form section names ("Final Chorus", "Verse 2", "Pre-Chorus", "Build-Up", "Chorus Reprise", "Coda") resolve to normalized identity + family through conservative keyword/phrase matching with plural handling; unknown names stay neutral (confidence 0) and remain fully supported — no naming convention imposed.
- `analyzeSectionContext`: neighbors, energy deltas, normalized position over the sectioned song span, occurrence/family count via relationship keys (recognized families group by family; unrecognized names group by number-stripped normalized name, so "Jam 1"/"Jam 2" relate while "Section A"/"Part B" stay apart), first/last/near-boundary flags, family-change transition flag.
- `buildSectionHarmonyProfile` / `buildSongHarmonyProfiles`: seven independent dimensions (stability, movement, rhythm, complexity, tension, modal emphasis, contrast) as {preferred, flexibility} pairs — internal planning parameters, not measurements. Identity contributes only ≤0.15 biases (no preset dictionary); context, the section's own energy (deliberately weak on tension, none on stability/modal/contrast) and the existing chordGenSettings (density, complexity, modalEmphasis, variation, borrowing, cadence, preserveIdentity, sectionAware) shift the anchors; `sectionAware:false` reduces identity influence to a residual 0.25 instead of disabling analysis.
- Harmonic rhythm is meter-aware via the shared meter utilities (barTicks/beatOffsets/beatTicks): changes-per-bar plus concrete tick intervals and felt-beat intervals, with a rhythm shape descriptor (hold/regular/mixed/accelerating/decelerating) — no chord timing is placed and no 4/4 assumption exists (6/8 reports 2 felt beats, dotted-quarter beatTicks, compound flag).
- `contours.ts`: reusable stable/rising/falling/arch/valley/wave contour families with deterministic, bounded, duration-independent `evaluateContour`; any dimension may carry one. Profile contours take family from identity tendencies and ranges from the dimension's preference.
- Development roles (establish/repeat/develop/contrast) derive from family recurrence and preserveIdentity; repetition identity outweighs neighbor-boundary contrast for recurring sections.
- Tests: `tests/harmony-profiles.test.ts`, 43 tests covering the ten spec groups (identities, context/energy/settings sensitivity, repetition, unusual structures, contours, 3/4 & 6/8 meter, determinism, no-mutation, Phase 1 + schema regression). Suite total 126; tsc clean; vite build unchanged.

# Harmony engine (Phase 3 — phrase & cadence planning)

- Extends `src/engine/harmony/` with `cadences.ts`, `phrases.ts`, `plan.ts` plus an internal `planning.ts` (shared deterministic math, not re-exported); contracts added to `types.ts`, exports in `index.ts`. Still pure TypeScript: no React/Zustand/browser APIs, no new dependencies, no UI or store changes, manual workflow and orchestral Generate untouched.
- `planSectionPhrases(project, sectionProfile, options?)` divides a section into phrases with exact, bar-aligned, gapless, overlap-free coverage. Phrase lengths EMERGE from section length, profile activity (movement / rhythm density / inverse stability), rhythm shape (accelerating/decelerating/regular ordering), a mild felt-beat meter factor (capped ±25%, no four-beat model) and existing-chord anchors — one-, two-, three-, five-, uneven and extended phrases are all reachable; no four/eight-bar template and no static length table. Candidates are scored as WHOLE structures (length fit, shape fit, anchor fit) and picked seed-aware — coherent variation, not per-bar coin flips.
- Timing goes through the shared meter utilities (barTicks/barToTick) at 960 PPQ: 4/4, 3/4, 6/8 verified; one-bar sections plan as a single one-bar phrase; zero-length sections return an empty (valid) plan. Seed handling follows spec Option B via the existing `mulberry32`/`hashString` (imported from `engine/generate.ts`, never duplicated): identical (project, seed) → identical plan; the seed is echoed in `SongHarmonyPlan.seed`, never advanced or persisted.
- Phrase roles are seed-stable: the FIRST phrase carries the section's material identity (Phase 2 development role: establish/repeat/develop/contrast), the LAST carries arrival/departure (conclude for the song's final section, prepare before structural departures), middle phrases develop when contours actively evolve there, else continue. Each phrase also carries a broad direction (stability/movement/tension sampled from the section's contours and preferences with small interpretable role biases) — trajectories, not bar-by-bar commands.
- `cadences.ts`: `cadenceEnvironment` derives structural facts from Phase 1 primitives (leading tone, dominant-quality degree-5 triad, subdominant triad, tonic-triad stability, characteristic tones, symmetry) — no mode-name lookup. `compatibleCadenceFamilies` turns those into support-ordered approach families (functional-tonal, plagal, modal, stepwise, pedal, chromatic, coloristic); symmetrical scales never receive functional-tonal/modal entries, Locrian's diminished tonic also removes plagal, and every environment keeps ≥ 4 families so nothing is boxed in. `cadenceTendencies`/`planCadence` describe the intended arrival (resolved/open/suspended/transitional/deceptive/modal/ambiguous) as deterministic weighted tendencies bent by role, song end, final qualifier, the next section's identity, the cadence/complexity/modalEmphasis settings and symmetry — "resolved" stays reachable everywhere (modal and pedal resolutions included); no chord is ever selected or placed.
- `plan.ts`: `planSongHarmony(project, options?)` assembles the song blueprint — chronological `PlannedSection[]` with phrases, cadences, and `SectionBoundaryPlan` seams (continuation/preparation/resolution/contrast/suspension/abrupt) from `boundaryTendencies` (energy delta, family change, outro/breakdown/final-qualifier identities, return-to-familiar material, the ending cadence). `sectionAware:false` halves contextual shifts instead of disabling analysis; `variation` controls pick entropy via a documented exponent mapping.
- Repeated material (spec §4): the first occurrence of a relationship group establishes a reusable form; later same-length occurrences reuse it when `preserveIdentity` is on (boundaries shared, roles shift to repeat/develop), different-length repeats plan freshly and link phrases proportionally (nearest normalized center) — related, never force-identical. Links are explicit `relatedPhraseIds` so Phase 4 decides how much to preserve.
- Existing chords (spec §11) are read-only context via `collectExistingHarmony` (chord-change ticks; locked spans clamped to the section). Chord starts make nearby boundaries more plausible (weight 0.5) and locked starts act as anchors (weight 1.0) — soft scoring only: a sustained chord may span a boundary, a phrase may contain several chords, and no chord is moved, resized, deleted or replaced.
- Tests: `tests/harmony-phrases.test.ts`, 31 tests in the ten spec groups (coverage/gaplessness, odd lengths 1–13, 4/4·3/4·6/8 tick math, structural boundary tendencies without mandated cadences, mode-derived cadence compatibility incl. all three symmetrical scales, chord anchors with byte-identical chord arrays, repeated-section form reuse and proportional links, seed determinism with non-moving section spans, very short songs, Phase 1/2 + orchestral-generator regression). Suite total 157; tsc clean.
